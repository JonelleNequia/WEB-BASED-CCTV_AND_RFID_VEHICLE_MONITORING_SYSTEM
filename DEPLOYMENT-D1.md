### macOS minimum and Intel decision

The **current Apple Silicon dependency set cannot support below macOS 14** because of its ORT wheel. Recommend **macOS 14 as the first candidate minimum for both Mac packages**, then certify it only after inspecting the chosen PHP/Caddy/go2rtc binaries and testing actual macOS 14 machines. D1's host is arm64/macOS 26.6.1: passing tests there does not establish a 14.x floor.

The current Intel package has **no valid minimum OS**, because its pinned dependency graph cannot be assembled natively. Upstream [PyTorch 2.2 release notes](https://github.com/pytorch/pytorch/releases/tag/v2.2.0) identify 2.2.x as the final macOS x86 release series. Metadata confirms available Intel CPython 3.12 candidates for Torch **2.2.2**, Torchvision **0.17.2**, ORT **1.23.2** or **1.20.1**, and OpenCV **4.10.0.84**. A candidate lock using NumPy **1.26.4**, matched full/headless OpenCV versions and a fully resolved scientific stack requires native model/algorithm/security testing. It is not an approved lock. Alternatively maintain a reviewed native Torch build. D3 must resolve this maintenance decision; Rosetta, Windows wheels and copying an arm64 venv are not solutions.

Ultralytics metadata declares AGPL-3.0. Its [licensing documentation](https://www.ultralytics.com/license) distinguishes AGPL and Enterprise licensing. Review the intended distribution with PHILCST, retain applicable source/notices or obtain the appropriate rights; a manifest's MIT label on one plate model does not resolve the whole dependency/model set. This is an unresolved redistribution review, not a legal conclusion.

## 3. Proposed package contents and installation flow

Final D6 artifacts, all rebuilt from **one clean, tested full source commit**, should be labeled:

- **Windows Complete Offline Package** — native AMD64 installer + optional verified ZIP.
- **Intel Mac Complete Offline Package** — x86_64 installer/archive, only after the Intel lock is accepted.
- **Apple Silicon Mac Complete Offline Package** — native arm64 installer/archive.
- **Connect to Server — Windows** and **Connect to Server — Mac** — small client helpers; no database, detector or server services.

Each server artifact contains application code/production vendor/local assets, native PHP, native Python plus all locked packages/libraries, verified models/configs, Caddy, go2rtc, appropriate service helpers, optional explicitly supported OCR/transcoding executables, documentation, licenses/SBOM, checksums and a signed manifest. No `.env`, database, media, live configuration, passwords, setup code or private CA key is distributed. Preserve source-export rejection checks and add post-build recursive artifact inspection.

Use semantic versions such as `v1.0.0-rc.1` with filenames containing OS/architecture and version. `BUILD-INFO.json` records full source SHA, lock/manifest hashes, native runtime versions, build environment/toolchain, architecture/minimum OS and test results. A per-file manifest covers extracted model and native-library bytes. Sign checksums/manifests with a maintained release key; a checksum downloaded beside a tampered archive is not publisher authentication. Software signing identity and an installation's TLS CA are separate.

**Builder only:** internet access, Git/Composer, Node/npm, wheel download/resolution, compilers/SDKs, Inno and signing/notarization. Lock all inputs; do not use mutable `latest` links without an immutable recorded result. Do not mix checkout HEAD with uncommitted build inputs. Windows native import checks need ORT, fast-plate-ocr and actual model inference in addition to current imports. Test dependency closure rather than trusting `--no-deps` pins. Python venv symlinks, development paths and user caches must not enter artifacts.

**Target installer:** verify manifest/version/architecture/space/conflicts, choose **This computer only** or **Share on local network**, place code/runtimes, create protected writable state, generate installation-specific APP_KEY/API secret/CA keys, provision a new local SQLite only when none exists, run approved additive migrations and `InstallSeeder` only for fresh non-account data, then issue protected first-admin setup delivery. Existing installations keep keys/accounts/names/media/configuration. Reinstall never silently creates a new DB or administrator. Finish with status, the shortcut, setup instructions and local recovery help.

Retain the current Windows root contract initially to avoid breaking existing installs. For Macs, plan root-owned application/runtime releases and protected shared data under `/Library/Application Support/PHILCST-VMS`, with a signed Open/Status helper in `/Applications`. Exact signed-bundle layout, writable cache/environment routing and dylib relocation are D3 work; never rely on Homebrew paths or mutate signed code to store data. Use absolute quoted working directories and test paths containing spaces. Both packages expose the same operator actions: Open, Status, Start, Stop, Backup, Restore and Update.

## 4. Named address, offline HTTPS and client connection

Canonical browser address: **`https://philcst.vms.internal`**, on port 443. Do not rename the OS computer or rely on `.local` multicast for this name. A fixed browser port avoids per-client URLs; detect conflicts instead of silently taking another application's port. Check 80/443, FastCGI, go2rtc API/media, detector and reader listener ports, existing service ownership and hostname entries before changes.

For **This computer only**, map the hostname to loopback on the server, bind browser/media listeners to loopback and add no LAN inbound rules. For **Share on local network**, use Ethernet where possible and a DHCP reservation or administrator-managed static LAN address. Use school/router DNS for the hostname when available; otherwise the Connect workflow adds one clearly managed hosts-file entry on each client. Detect contradictory/duplicate mappings, preserve unrelated entries, and provide idempotent repair/removal. Main-computer mapping can remain loopback. Clients map the name to the server's reserved LAN IP. No DNS or certificate operation needs internet.

Caddy's [internal issuer](https://caddyserver.com/docs/automatic-https) supports local certificates without a public CA. In D4 use explicit `tls internal`, durable installation-local Caddy storage and explicit trust installation; [skip automatic trust mutation](https://caddyserver.com/docs/caddyfile/options#skip-install-trust). Generate the CA on first install, never in the release bundle. Protect root/intermediate private keys with service-only ACLs/permissions; keep public root export separate. Set secure cookies/external URL/proxy handling correctly. Keep internal authenticated API traffic on a separately configured loopback endpoint, or explicitly configure Python to trust the local root; never disable TLS verification to make requests work.

The client helper asks for the server's stable IP and verifies the installation's root-certificate fingerprint through an independent administrator/USB handoff. It imports **only that public root certificate**, configures resolution, tests HTTPS/login/media and makes an Open shortcut. On Windows use the intended Root trust store with explicit elevation; on Mac use the system keychain with explicit elevation. Test Firefox trust separately rather than assuming every browser follows the OS store. A client helper must never create a DB, install collectors, copy APP_KEY/device credentials or issue another CA.

Keep the CA state across reboot/reinstall/update. Caddy handles leaf/intermediate renewal while running, but test it with internet blocked and correct local time. Provide CA-expiry/status warnings and an explicit root-rotation/re-enrollment procedure. Back up CA private state separately/protected with the deployment; an authorized transfer can preserve the CA and clients' trust after fencing the old server, or intentionally rotate it and reconnect every client. Do not silently regenerate a CA during repair. Allow offline local time administration/local NTP; do not require public NTP. Mac notarization/signing can use internet on the build machine; [stapling and Gatekeeper behavior](https://developer.apple.com/documentation/security/customizing-the-notarization-workflow) must be validated on disconnected targets.

### Media and access review

- `OccurrenceMediaController`, `OccurrenceMedia`, authenticated `/evidence/occurrences/...` and `CrossingSnapshotService` protect new referenced evidence and reject uncommitted files/conflicting context. Preserve these protections.
- Legacy images under `public/storage` remain directly served by `file_server`/the public symlink. New private storage does not retroactively protect those files. Plan an authenticated compatibility-serving path for referenced historical media, keeping DB evidence/path ownership intact; do not claim all old images are protected today.
- Preserve signed-in `/camera/...`, `/live/...`, SDP/HLS and `/detector/*` authorization. Keep raw 1984/8765/FastCGI on loopback. Expose only the approved browser port and necessary scoped WebRTC/reader transports in LAN mode. Validate HLS playlist/segment URLs, MJPEG and snapshots remain same-origin under HTTPS without mixed-content fallback.
- Existing WebRTC signaling is authenticated, while media uses negotiated transport on 8555. Long-lived streams/proxies need logout/account-disable/new-request acceptance tests; do not equate initial signaling authorization with continuous revocation.
- Integration controllers enforce the configured API key through `Api/Concerns/AuthorizesIntegration`; production must not enable the development keyless-loopback fallback. Retain protected exported runtime configuration and redact secrets in diagnostics.

## 5. Devices, background operation and compatibility limits

Current camera support includes RTSP/HTTP/ONVIF-derived sources and numeric local webcam capture. `CameraProbeService`, `CameraSource`, `devices/probes.py`, `module_config.py` and OpenCV govern actual compatibility. Establish an H264 baseline across Edge/Chrome/Safari; validate H265/transcoding only if packaged and tested. Browser clients do not connect directly to camera credentials or run OCR.

`devices/reader_link.py` implements TCP/UDP network reader connections, incoming reader listeners and protocol decoding. Tag entry also supports keyboard-style scanning and keyed HTTP integration. There is no general Python serial driver dependency such as pyserial: do not advertise universal USB/COM/RS232 support. A USB keyboard wedge and a USB serial reader are different integrations. Any vendor-signed drivers needed by an approved serial/USB device require an offline driver package and explicit licensing/native testing.

Windows services already continue without a browser. The detector's stream-port bind prevents a second local detector; managed mode keeps page requests from launching another. A busy port is not a deployment-wide lease: an unrelated process can occupy it, and another server can still collect the same devices. Detect legacy startup tasks/venvs and duplicate install roots. Add ownership-aware status/recovery rather than killing unrelated processes.

For Mac use launchd services with absolute paths, a service identity, logs/rotation, restart/backoff, startup ordering and health checks; use a controlled LaunchAgent/helper where an interactive privacy grant is unavoidable. [Apple local-network privacy](https://developer.apple.com/documentation/technotes/tn3179-understanding-local-network-privacy) affects modern macOS and per-user identities. Camera/microphone permission, local-network discovery, firewall prompts and signing attribution need real OS testing. Do not promise pre-login USB-webcam capture from a headless daemon. Verify FileVault/login, sleep and locked-screen behavior. Document AC power/no-sleep policies as intentional operator settings; retain previous settings for uninstall rather than unconditionally changing every network/power profile.

Hardware acceptance must include the actual school camera and RFID models, reboot/network reconnection, dropped frames, reader reconnects, NIC/subnet discovery, shared-camera configurations and at least two gates under representative client load. CPU-only operation is required as the baseline; minimum RAM, CPU ISA and throughput need measured native artifacts, not Mac development benchmarks.

## 9. Blocking decisions and handoff

1. **Release source:** decide which already-tested working-tree changes belong in the reviewed release commit. D1 does not commit them. Current builder would omit them from app source while potentially reading changed build inputs.
2. **Intel Mac:** select and maintain a compatible native dependency graph/build. Current pins cannot produce this package. macOS 14 is a candidate floor, not a support claim until native binaries and minimum-OS tests pass.
3. **Redistribution/signing:** confirm model/dependency obligations and software signing/notarization identities. Resolve exact portable Mac PHP/Python suppliers/builds, VC++ hash pin, OpenCV provider collision and whether Tesseract/transcoding are included in the supported feature baseline.
4. **Recovery/availability:** durable delivery, consistent update/backup/restore, denylist permanence, context freeze and old-server fencing are release gates. Current happy-path tests do not close these findings.
5. **Native access:** Windows 10/11, Intel Mac and macOS 14 test machines; Windows/Mac LAN clients; approved cameras/readers and any claimed USB drivers are unavailable to this audit. Offline CA trust/renewal and Gatekeeper/service privacy behavior need those tests.
